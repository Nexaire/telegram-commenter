# Telegram-монитор заявок на кавер-группу

Сервис читает заданные Telegram-каналы и чаты через обычный пользовательский
аккаунт, находит заявки на кавер-группу и публикует их отдельным ботом в рабочий
канал. Никаких комментариев и текстов от ИИ сервис не создаёт.

У новой заявки есть кнопки:

- **Открыть** — открыть исходное сообщение;
- **В работу** — заменить кнопки статуса на **Договорились** и **Отказ**;
- **Не заявка** — пометить ошибочное совпадение и оставить только **Открыть**.

После **Договорились**, **Отказ** или **Не заявка** остаётся только кнопка
**Открыть**. Менять статусы могут только пользователи из `MANAGER_USER_IDS`.

Каждое утро бот присылает в рабочий канал статистику за последние 24 часа:
сколько заявок найдено, сколько из них всё ещё новые, взято в работу и признано
не заявками. Ниже выводится полный список всех необработанных заявок в статусе
«Новые», включая найденные раньше суток.

## Как всё устроено

Здесь используются две разные Telegram-учётки:

1. **Пользователь Александр** через Telethon читает источники. Его авторизация
   хранится в `data/cover-monitor.session`.
2. **Отдельный Telegram-бот** публикует найденное, показывает кнопки, принимает
   нажатия и отправляет отчёт.

SQLite в `data/monitor.db` хранит найденные сообщения и статусы. Уникальная пара
«источник + номер сообщения» защищает от дублей. Пропущенные после перезапуска
сообщения дочитываются автоматически. Ошибки отправки повторяются с
увеличивающейся паузой, а Telegram `RetryAfter`/flood control соблюдается.

## Пошаговая первоначальная настройка

Ниже команды рассчитаны на сервер, где проект находится в
`/opt/telegram-commenter` и уже установлен Docker Compose.

### Шаг 1. Получить свежий код

~~~bash
cd /opt/telegram-commenter
git pull
~~~

Проверка:

~~~bash
git log -1 --oneline
docker --version
docker compose version
~~~

### Шаг 2. Создать управляющего бота

1. Откройте в Telegram официального [@BotFather](https://t.me/BotFather).
2. Отправьте `/newbot`.
3. Задайте любое отображаемое имя, например `Wayfreeband Leads`.
4. Задайте свободный username, обязательно заканчивающийся на `bot`, например
   `wayfreeband_leads_bot`.
5. Скопируйте выданный token. Он выглядит примерно как
   `123456789:AA...`. Никому его не отправляйте и не добавляйте в Git.

### Шаг 3. Добавить бота в рабочий канал

Рабочий канал: **Заявки для Wayfreeband**, ID `-1004456489930`.

1. Откройте канал → **Управление каналом** → **Администраторы**.
2. Добавьте созданного бота.
3. Разрешите ему публиковать и редактировать сообщения.

Обычного добавления подписчиком недостаточно: бот должен быть администратором.

### Шаг 4. Заполнить `.env`

Если файла ещё нет:

~~~bash
cp .env.example .env
nano .env
~~~

Заполните его так, подставив реальные API ID, API hash и новый bot token:

~~~env
TELEGRAM_API_ID=12345678
TELEGRAM_API_HASH=ваш_api_hash
TELEGRAM_SESSION=/data/cover-monitor.session

DATABASE_PATH=/data/monitor.db
CHANNELS_CONFIG=/app/config/channels.yaml
LOG_LEVEL=INFO
DRY_RUN=true
MONITOR_LOOKBACK_HOURS=24
MONITOR_POLL_SECONDS=300

LEAD_BOT_TOKEN=123456789:токен_от_BotFather
MANAGER_USER_IDS=5488372876
REPORT_TIMEZONE=Europe/Moscow
REPORT_HOUR=9
REPORT_MINUTE=0
~~~

`5488372876` — Telegram ID Александра Жалейко. Чтобы дать доступ нескольким
людям, перечислите их ID через запятую: `5488372876,123456789`.

Время отчёта в примере — 09:00 по Москве. Допустимые часы: `0`–`23`, минуты:
`0`–`59`. После запуска позже заданного времени бот отправит ещё не отправленный
отчёт за текущую дату сразу.

`TELEGRAM_API_ID` и `TELEGRAM_API_HASH` получают на
[my.telegram.org](https://my.telegram.org/) → **API development tools**. Это
данные пользовательского клиента, они не заменяют token от BotFather.

Сохранение в `nano`: `Ctrl+O`, Enter, затем `Ctrl+X`.

### Шаг 5. Настроить источники

Откройте файл:

~~~bash
nano config/channels.yaml
~~~

Рабочий пример:

~~~yaml
target_channel: -1004456489930

matching:
  keywords:
    - "кавер-групп"
    - "кавер групп"
    - "кавер-бэнд"
    - "кавер бэнд"
    - "cover band"

  require_intent: false
  intent_phrases:
    - "ищем"
    - "ищу"
    - "нужна"
    - "нужны"
    - "требуется"
    - "посоветуйте"
    - "на свадьбу"
    - "на корпоратив"
    - "на мероприятие"

  exclude_phrases:
    - "мы кавер-группа"
    - "мы кавер группа"
    - "наша кавер-группа"
    - "наша кавер группа"

sources:
  - entity: -1001297680727
    enabled: true
  - entity: -1001460649499
    enabled: true
  - entity: -1001168970187
    enabled: true
  - entity: -1001674976711
    enabled: true
  - entity: -1001290898972
    enabled: true
  - entity: -1001857821570
    enabled: true
  - entity: -1001101256505
    enabled: true
~~~

Пользовательский аккаунт должен быть участником каждого приватного источника.
Список доступных ему диалогов можно проверить так:

~~~bash
docker compose run --rm commenter python -m app.list_dialogs
~~~

В начале вывода должно быть:

~~~text
ACCOUNT: Александр Жалейко (@azhaleiko, id=5488372876)
~~~

### Шаг 6. Создать или проверить пользовательскую сессию

Если `data/cover-monitor.session` уже есть и команда из предыдущего шага
показывает Александра, ничего заново авторизовывать не надо.

Если файла нет или указан неправильный аккаунт:

~~~bash
mkdir -p data
rm -f data/cover-monitor.session data/cover-monitor.session-journal
docker compose build
docker compose run --rm commenter python -m app.init_session
~~~

Введите номер телефона нужного аккаунта, код из Telegram и пароль 2FA. Файл
сессии — секрет уровня пароля. Не копируйте его посторонним и не добавляйте в Git.

Если контейнер сообщает, что не может записать файл в `/data`:

~~~bash
sudo chown -R 10001:10001 data
~~~

### Шаг 7. Безопасно проверить поиск

Пока оставьте `DRY_RUN=true`, затем запустите:

~~~bash
docker compose up -d --build --force-recreate
docker compose logs -f --tail=200 commenter
~~~

Нормальный запуск содержит события `workflow_bot_started` и семь
`source_registered`. Ошибок быть не должно.

Опубликуйте в одном из источников тестовый текст:

~~~text
Ищем кавер-группу на корпоратив 20 декабря. Москва.
~~~

В логах должно появиться `match_detected`, затем `match_dry_run`. В рабочий канал
в безопасном режиме ничего не придёт. Выйти из просмотра логов: `Ctrl+C`; сам
контейнер продолжит работать.

### Шаг 8. Включить настоящую публикацию

Откройте `.env` и замените:

~~~env
DRY_RUN=false
~~~

Перезапустите сервис:

~~~bash
docker compose up -d --build --force-recreate
docker compose logs -f --tail=200 commenter
~~~

Теперь **новое** подходящее сообщение должно прийти в канал с кнопками. Запись,
которая уже была сохранена во время `DRY_RUN`, повторно не публикуется — это
защита от дублей. Для финальной проверки отправьте ещё одно новое тестовое
сообщение или дождитесь настоящей заявки.

Проверьте по порядку:

1. **Открыть** ведёт на исходное сообщение.
2. **В работу** оставляет **Открыть**, **Договорились** и **Отказ**.
3. **Договорились** или **Отказ** оставляет только **Открыть**.
4. На другой новой заявке **Не заявка** оставляет только **Открыть**.

Кнопки появятся только у новых сообщений, опубликованных ботом после обновления.
Добавить inline-кнопки к старому сообщению, ранее опубликованному пользовательским
аккаунтом, бот не может.

### Шаг 9. Быстро проверить утренний отчёт

Чтобы не ждать утра, временно задайте в `.env` время на 2–3 минуты позже текущего
московского времени, например:

~~~env
REPORT_HOUR=14
REPORT_MINUTE=37
~~~

Затем перезапустите контейнер:

~~~bash
docker compose up -d --force-recreate
docker compose logs -f --tail=100 commenter
~~~

В указанное время должен прийти отчёт, а в логах появится
`daily_report_sent`. После проверки верните `REPORT_HOUR=9` и
`REPORT_MINUTE=0`, затем ещё раз перезапустите контейнер.

Отчёт отправляется только один раз за календарную дату. Если тестовый отчёт уже
пришёл сегодня, повторная смена времени не создаст второй отчёт. Следующий отчёт
автоматически придёт завтра.

~~~bash
cd /opt/telegram-commenter
git pull
docker compose up -d --build --force-recreate
docker compose ps
docker compose logs --tail=100 commenter
~~~

## Если что-то не работает

Показать состояние и последние логи:

~~~bash
cd /opt/telegram-commenter
docker compose ps
docker compose logs --tail=200 commenter
~~~

Частые причины:

- `LEAD_BOT_TOKEN is required` — token не записан в `.env`;
- `InvalidToken` или `Unauthorized` — token скопирован неверно либо отозван;
- `Chat not found` — бот не добавлен в канал или неверен `target_channel`;
- `Forbidden: not enough rights` — бот не администратор или ему запрещена
  публикация;
- `At least one MANAGER_USER_IDS` — не указан Telegram ID управляющего;
- на кнопке появляется `Нет доступа` — ID нажавшего отсутствует в
  `MANAGER_USER_IDS`;
- источник не регистрируется — пользователь Александр не состоит в нём либо ID
  указан неправильно;
- ссылка `t.me/c/...` не открывается — нажавший пользователь не состоит в
  приватном источнике;
- бот отвечает на кнопки нестабильно — этот же token одновременно запущен на
  другом сервере; один token должен обслуживаться одним экземпляром сервиса.

## Ограничения ссылок Telegram

- Публичное сообщение получает ссылку `https://t.me/username/message_id`.
- Приватный канал или супергруппа получает ссылку `https://t.me/c/...`; открыть
  её могут только участники источника.
- У старой обычной приватной группы стабильной ссылки нет, поэтому кнопки
  **Открыть** у такой заявки не будет.

## Разработка и тесты

~~~bash
python -m pip install -r requirements-dev.txt
pytest -q
ruff check app tests
~~~

Основные события в логах:

- `workflow_bot_started` — бот кнопок запущен;
- `source_registered` — источник подключён;
- `match_detected` — совпадение записано в очередь;
- `match_dry_run` — совпадение найдено в безопасном режиме;
- `match_published` — заявка опубликована;
- `lead_status_changed` — пользователь изменил статус;
- `daily_report_sent` — утренний отчёт отправлен;
- `bot_flood_wait` — Telegram попросил подождать;
- `match_publish_failed` или `daily_report_failed` — операция завершилась ошибкой.
